# ADR-0021: Agents write docs into a folder the user picks; valk renders them and carries comments back

Status: proposed (2026-11-09)
Date: 2026-11-09

## Context

Agents write a lot of markdown that a person is meant to read: plans, research,
reports, handoffs, comparisons. Today it scatters. Some lands in `.omc/plans/`, some
in `docs/`, some in chat scrollback, some nowhere. The user reads most of it in
Obsidian, if they find it at all. None of it says which session wrote it, and
there's no way to answer it except to find the session and type into it.

Valkyrie already has the parts for a better path:

- **A markdown renderer** shared by the chat and the decision cards
  (`web/src/components/Markdown.tsx`, backlog #130).
- **Provenance from the connecting peer** (ADR-0007 §4, ADR-0017 §2). The daemon
  works out which session and agent is asking from the process itself, never from
  what the client claims.
- **A project key per repository** (ADR-0007 §2). Every worktree resolves to the
  main checkout, and the context store already names projects `<name>-<hash>`, so
  two repos called `api` never collide.
- **A way to tell a session something at its next prompt.** The backlog already
  uses it to say "the user accepted #N you filed" (`Registry::accepted_for`,
  delivered by the `UserPromptSubmit` hook).
- **The web app is reachable from paired devices** (ADR-0009). Anything it can
  show is readable over the network by any paired device, so what it may read has
  to be fixed by the user, not by an agent.

Obsidian is the user's editor and will stay so. Valkyrie shouldn't compete with it
as an editor. What it can add is the part Obsidian can't: who wrote a doc and why,
and a way for a comment to reach the agent that wrote it.

## Decision

1. **The docs root is a folder the user picks.** It's set with `valk doc root
   <path>` (later, from the web app's Settings too), usually a folder inside an
   Obsidian vault (`~/vault/valk`), and kept in `<state dir>/docs.json`, not
   `settings.toml`: the TUI rewrites that file from the fields it knows. With no
   setting, the root is `<state dir>/docs`, so docs work without Obsidian. Your home
   folder or `/` is refused as too wide. Only a human can set or change it: the
   daemon refuses `DocsRoot` with a path from an agent, the same way it refuses
   reviews (ADR-0007 §4). Otherwise an agent could aim the root at `~/.ssh` and have the web app
   serve it. Changing the root moves nothing: the old folder stays where it was.

2. **Layout: agent-level docs at the top, one folder per repository below.**
   ```
   <root>/
     2026-11-09-homelab-backup-plan.md     agent-level, cross-repo, life
     repos/
       valkyrie/
         2026-11-09-docs-viewer-research.md
   ```
   - A doc written from inside a repository goes to that repository's folder.
     `--global` (or not being in a repository) puts it at the top. Worktrees share
     their repository's folder.
   - **Folder names:** a repository gets its directory name (`valkyrie`). If a
     different repository already holds that name, the newcomer gets
     `<name>-<hash>`: the context store's own project hash (ADR-0007 §1), cut to 6
     characters, so a repository has one name scheme everywhere. The daemon records which project key owns
     which folder in `<state dir>/docs.json`, so the choice is made once and never
     reshuffled. A folder the user renamed in Obsidian is followed by the id in each
     doc's front matter (item 3), not by its name.
   - Files are `YYYY-MM-DD-slug.md`. The daemon makes the slug from the title. It
     never takes a path or file name from the client.
   - There are no kind subfolders (`plans/`, `research/`). The kind is a front
     matter field, which Obsidian's properties can filter on, so agents never have
     to choose a folder.

3. **Agents write docs through the daemon, with provenance.**
   - Agents write with `valk doc write "<title>" [--kind plan|research|report|note] [--global] -`
     (body on stdin) or MCP `write_doc`.
   - The daemon writes the file atomically (`O_EXCL`, temp file + rename) and adds
     front matter in YAML so Obsidian reads it as properties: `valk-id`, `kind`,
     `title`, `created`, `by` (agent), `session`, `conversation`, `commit`, `item`
     (the backlog item the session is on, if any), `repo`. As with notes
     (ADR-0017 §2), the daemon fills in session, conversation and commit from the
     peer and the checkout itself. It doesn't take them from the client.
   - Bodies are cleaned like decisions': no control characters, no bidi overrides.
     The size cap is 200 KB.
   - The daemon never follows a symlink out of the root, and it refuses a root, or a
     folder under it, that resolves outside the root.
   - The `SessionStart` block gets one line telling agents that human-facing
     markdown goes through `valk doc write`, not into the repository or `/tmp`.

4. **Agents and the user edit the same docs. No edit is lost, and every replaced
   version is kept.** Docs are meant to be worked on together: the user writes in
   Obsidian, an agent revises, the user edits again.
   - **Any agent may edit any doc under the root**, including one the user wrote or
     one another agent wrote: `valk doc read <valk-id>` / MCP `read_doc`, then
     `valk doc edit <valk-id> --base <hash> -` / MCP `edit_doc`. `read` returns the
     text and its hash.
   - **An edit has to be based on what's on disk.** The daemon replaces the file
     only if its hash still matches `--base`. If anyone saved since the agent read
     it (the user in Obsidian, the web app, another agent), the edit is refused with
     the current text. The agent merges its change into that text and tries again.
     So an agent never writes over an edit it hasn't seen.
   - **Every replaced version is kept** in `<state dir>/docs-history/<valk-id>/`
     (the last 50, 30 days; outside the docs folder, so the default root never
     lists them). Each edit saves the file as it was on disk just before, so a
     version the user saved in Obsidian is kept as well as the agent's. The web app
     shows a doc's history and restores a version in one tap, so a bad agent edit
     costs nothing. Between two edits, only Obsidian's own history holds the user's
     intermediate saves.
   - Each edit adds a line to `edited` in the front matter (who, session, when),
     so a doc shows who has touched it, not just who wrote it.
   - A doc with no `valk-id` (one the user made in Obsidian) gets one the first
     time an agent reads it.
   - The daemon never deletes a doc. Deleting is the user's job, in Obsidian or
     with one tap in the web app. A web app delete names the hash it loaded, like an
     edit, and keeps the file in `<state dir>/docs-trash/` (same limits as the
     history) so its Undo can put it back, never over a file that took its name. Obsidian Sync's conflict copies
     (`… (conflict …).md`) are listed like any other doc and never written to.

5. **The web app gets a Docs view.**
   - **The list:** agent-level docs, then each repository's, newest first, with
     kind, author agent and session.
   - **Unread:** a doc an agent wrote since you last opened the list shows as unread.
     The Inbox shows a count, not a card for each doc. Reading a doc is optional, not
     a review (ADR-0011's review budget), so it never queues anything.
   - **Rendering** uses the shared `Markdown` component, which gains real tables,
     read-only task lists, and `[[wikilinks]]` to other docs under the root. HTML in
     a doc is shown as text, never rendered. Only `http(s)` links open, as in chat.
   - **The web app asks for docs by `valk-id`, never by path.** The daemon looks up
     the file, checks that it's under the root, and sends the text over the existing
     WebSocket. No HTTP route serves files.
   - The daemon indexes the root on request: it scans `*.md` files, skips dotted
     folders (`.obsidian`, `.trash`), and caches by mtime. Docs without a `valk-id`
     are listed as the user's own, read-only in this phase.

6. **Comments go back to the session that wrote the doc.**
   - From the web app, you can comment on a block (a heading, paragraph, list item
     or code block) or on the whole doc.
   - Comments live in a sidecar file, `<state dir>/docs/comments/<valk-id>.jsonl`,
     not in the markdown, so the file stays clean for Obsidian, and commenting
     never counts as an edit that makes an agent re-read the doc (item 4). Each comment records the quoted block text,
     because blocks shift as a doc changes.
   - If the authoring session is still running, the comment reaches it at its next
     prompt through the same path the backlog uses: "On your doc *<title>*, about
     '<quote>': <comment>". When it edits the doc in reply, the comment shows as
     answered.
   - If the session is gone, the comment stays open on the doc. A later phase can
     offer to start a session on it.
   - Only a human comments. A comment an agent reads is framed as the user's words
     about its own doc.

7. **Editing in the web app is light.** A textarea with a preview, saved under the
   same rule as an agent's edit (item 4): the hash it loaded must still be on disk.
   If an agent or Obsidian saved in between, the save is refused and both versions
   are shown side by side. Heavy editing belongs in Obsidian.
   - The editor changes the body; the front matter stays as it was, plus an
     `edited` line for the user. One of the user's own docs gets a `valk-id` on
     its first save, so it has a history from then on.
   - Saving, restoring and deleting go by the key the list gave out (§5), never a
     path, and the daemon takes them from a human only. `EditDoc` stays the
     agents' path.
   - A restore puts an old version's body back under the same hash rule; what it
     replaces joins the history, so a restore is undone the same way.

8. **Agents don't get docs injected.** No hook or block carries another doc's text.
   An agent reads docs only by asking (`valk doc list` / `valk doc read`, MCP
   `list_docs` / `read_doc`; word search later).
   Results are framed as unreviewed, with session and commit, the way notes are
   (ADR-0017 §4). Decisions and skills stay in the context store. Docs are output
   for a person, not context for agents.

## Phases

1. **Store and write path.** The `docs` setting (human-only), folder mapping,
   `valk doc write|read|edit` and their MCP tools, front matter, the base-hash
   check, version history, the `SessionStart` line.
2. **Docs view.** List, unread count, rendering with tables, task lists and
   wikilinks, lookup by id.
3. **Comments.** Sidecar, delivery to the live session, answered state.
4. **Light editing**, history and restore, and delete in the web app.

Each phase is a separate backlog item. Phase 1 is useful on its own, since Obsidian
already shows the files.

## Consequences

- One place for agent output, readable in Obsidian on the desktop and in valk on the
  phone, with each doc tied to the session and commit behind it.
- The daemon stops being the only writer for this one store (amends ADR-0007 §3
  for docs only). Two things keep the user's work safe from it: edits must start
  from what's on disk, and every replaced version is kept (item 4).
- Any agent can rewrite any doc under the root. That's deliberate, for working
  together, and it's why the root is a folder for agent work, not the whole vault.
  An agent that rewrites a doc badly is undone from its history.
- The web app now reads files in a folder the user picked. The id-only lookup and
  the root check are the security boundary, and phase 2 gets a security review
  before it ships. An agent that runs arbitrary code can still write files under
  the root directly. As in ADR-0007, that's the agent sandbox's problem; such a
  file just shows up without a `valk-id`, as the user's own.
- Agents need telling: without the `SessionStart` line, docs keep landing in
  `.omc/plans/` and `/tmp`.
- Comments add a new kind of text typed into an agent's next prompt. It's the
  user's own words, so it carries no more risk than the user typing it.

## Not now

A read-only mirror of decisions and skills into the vault, images and embeds,
mermaid, starting a session from an orphaned comment, delivering comments to Codex
sessions (phase 3 covers Claude's prompt hook first), syncing docs across machines (Obsidian Sync
or git already do it), and full-text search ranking beyond ADR-0014's matcher.
